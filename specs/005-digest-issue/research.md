# Research: Weekly Digest Issue

**Branch**: `005-digest-issue` | **Date**: 2026-09-24 | **Spec**: [`spec.md`](./spec.md)

The `/speckit-clarify` session closed the product questions (cadence, translation wait, owner
editing, traceability, the 002 amendment). What is left are **technical** decisions: where each
piece of work runs, how single-flight translation is enforced, and how the schema changes roll
out safely. Each decision lists what was chosen, why, and what was rejected.

Verified against the installed versions: Payload `3.88.0` (collection `indexes` with
`{ fields, unique }` exists), `@payloadcms/db-postgres` `3.88.0`, Next.js `16.3.3` (`after()`,
`htmlLimitedBots`), next-intl `4.13.7`, `ai` `7.0.79`.

---

## R1 — An issue is a published digest; no new "Issue" collection

**Decision**: Extend the existing `digests` collection with the issue fields: summary points,
per-item sentences, generation status, text revision, and a hidden flag (see
[`data-model.md`](./data-model.md)). The public URL uses the digest id:
`/{locale}/projects/{slug}/issues/{issueId}`. The archive lives at `/{locale}/projects/{slug}/issues`.

**Rationale**: The spec defines exactly one issue per published digest. A second collection
would need its own 1:1 invariant, a create hook, and a backfill, and would add nothing.
Digest ids are numeric Postgres ids and are never reused, so the URL is stable (FR-001). The
route shape matches the roadmap's spec queue.

**Alternatives considered**:

- _Separate `issues` collection with a `digest` relation._ Rejected: duplicates identity and
  needs a sync hook on the Vercel request path, which already caused 504s (`digestHooks.ts`).
- _Date-based URL (`/issues/2026-09-28`)._ Rejected: not unique if a project ever publishes
  twice in a day (manual run, catch-up digest), and it needs a timezone rule. The date is shown
  in the title and metadata instead.

## R2 — The worker generates issue text in an end-of-job sweep

**Decision**: Issue text (summary points and per-item sentences, English) is generated by
`apps/worker`. At the end of every hourly job, after due projects have run, a **sweep** picks up
every digest whose `issueTextStatus` is `pending`, is unset (digests from before this feature),
or is `failed` with `issueTextAttempts < 3`. It generates the text and PATCHes the digest over
Payload REST. A new digest is created with `issueTextStatus: 'pending'`, so it gets its text in
the same job execution that published it, a few minutes later.

The one sweep covers four requirements with one code path:

| Need                                    | How the sweep covers it                                               |
| --------------------------------------- | --------------------------------------------------------------------- |
| Generate on publish (FR-014)            | New digest is `pending`; same job's sweep generates it.               |
| Backfill old digests once (FR-014)      | Pre-feature rows have no status; first sweep after deploy fills them. |
| Failure is logged via alerting (FR-015) | `logError` → Cloud Logging ERROR → existing log-based alert.          |
| Owner "regenerate" (FR-021)             | Owner sets status to `pending` in admin; next hourly sweep runs it.   |

**Rationale**:

- **Principle VII.** Generation is pipeline work. The worker already holds the AI client, prompt
  hygiene (`escapeUntrusted`), and the ERROR-log alert policy from spec 004. Vercel runtime
  errors are **not** wired to any alert, so FR-015 ("recorded as an error through existing
  alerting") is only met out of the box if generation runs in the worker.
- **No request-path LLM work on publish.** Running generation inside the `Digests`
  `afterChange` hook would put 5–20 s of LLM calls inside the worker's `POST /api/digests`,
  which is the exact path that timed out before.
- **Free tier.** The sweep adds one `GET /api/digests` per hourly tick and LLM calls only when
  there is work.

**Trade-off accepted**: an owner-requested regeneration takes effect at the next hourly tick
(≤ 1 h), not instantly. The admin field description says so. Manual **edits** are immediate.

**Alternatives considered**:

- _Generate in the web app with `after()` on publish or on an admin button._ Rejected: splits
  prompt and safety rules across two services, and the failures would not reach existing
  alerting.
- _Separate one-off backfill script (like `backfill-translations.ts`)._ Rejected: the sweep
  already treats "no status" as pending, so a script would be a second implementation of the
  same thing.
- _Generate inline in `runProject` right after `createDigest`._ Rejected: the sweep is still
  needed for backfill, retry and regeneration. Inline generation would be a second call site.

## R3 — Two-step generation, with numbered items and validation

**Decision**:

1. **Per-item sentences.** Items are sorted by the issue order (R14) and numbered `1..n`. They
   are sent in batches of ≤ 20 items per call. Structured output: `{ items: [{ n, sentence }] }`.
2. **Summary.** One call receives the numbered items (title, kind, the sentence from step 1, and
   importance). It returns `{ points: [{ text, items: number[] }] }` with 3–5 points (at least one per item
   when there are fewer than 3 items: `minSummaryPoints = min(3, n)`).
3. **Map and validate** (pure function, Jest-tested). Map `n` to publication ids. Then enforce:
   - every item has exactly one sentence of ≤ 35 words (the prompt asks for ≤ 30);
   - `min(3, n)`–5 points, ≤ 120 words in total (the prompt asks for ≤ 100, keeping headroom
     like sentences' 30 vs 35);
   - every point references ≥ 1 valid item number (invalid numbers are dropped, and a point left
     with no reference fails validation);
   - the guard patterns below find nothing.
4. On validation failure, retry the failing step **once**. If it still fails, set
   `issueTextStatus: 'failed'`, increment `issueTextAttempts`, store a short `issueTextError`,
   and call `logError`. After 3 failed attempts the digest stays `failed` until the owner
   re-queues it, so a broken prompt does not cost LLM calls and alerts every hour.

**Guard patterns** (defence in depth for FR-005/FR-006; SC-004 manual review is still the
acceptance check):

- Dose patterns in any text: `/\b\d+(?:[.,]\d+)?\s?(mg|mcg|µg|g|ml|iu|units?)\b/i`.
- Trial registration sentences must not claim outcomes:
  `/\b(results? (show|showed|suggest)|showed|demonstrated|proved|was (effective|safe))\b/i`.

**Rationale**: Summary points that cite item **numbers** make FR-007 traceability mechanical: the
model cannot link to an id it never saw, and validation rejects dangling references. Building
the summary from already-validated one-sentence descriptions keeps it grounded in the listed
items, not in the model's background knowledge. Batching keeps a 20+ item bootstrap digest
(like 2026-08-31) inside one call's comfortable context.

**Alternatives considered**:

- _One call that returns both summary and sentences._ Rejected: with 20+ items the output is long
  and partial failures are all-or-nothing. It is also harder to keep the summary tied to the
  items.
- _Free-text citations ("[1]") parsed out of prose._ Rejected: fragile. Structured `items: number[]`
  per point is exact.

## R4 — Prompt inputs and safety rules come from project data

**Decision**: The prompts receive:

- **Project context**: `name`, `keywords`, and a new optional `audienceContext` on
  `research-projects` (for example "people living with the condition and their families").
  If `audienceContext` is empty, the prompt falls back to "patients and families interested in
  {project name}".
- **Per item**: title, kind (`publication` or `trial registration: a planned or recruiting study
with no results yet`), `publicationTypes`, the stored English specialist summary
  (objective/results/limitations/whyItMatters), and the first 1,500 characters of
  `abstractOrBody`. Everything is wrapped in `<untrusted_content>` using the existing
  `escapeUntrusted`.

The system prompt carries the FR-003–FR-006 rules: plain words at roughly a school reading level;
no drug names given as advice, no doses, no treatment changes; nothing beyond what the item says;
cautious wording ("early", "small study", "may") for early or small studies; a trial registration
is described as planned or recruiting, never as having results.

**Rationale**: The spec assumption and roadmap §4 require disease and audience wording to come
from project data, with no literals in `apps/*/src`. The abstract excerpt grounds claims better
than the AI-derived specialist summary alone. The cap keeps weekly cost trivial on
`gpt-4o-mini`.

**Alternatives considered**: _Full abstract per item._ Rejected on cost and context size for
bootstrap-sized digests, with little gain for a one-sentence output.

## R5 — Weekly anchor lives in the due-check, driven by per-project fields

**Decision**: Keep the single hourly Cloud Scheduler job. Add two optional fields to
`research-projects`: `publishWeekday` (`monday`…`sunday`) and `publishHourUtc` (0–23). Extend
`packages/shared/src/schedule.ts`:

- `latestScheduledSlot(schedule, anchor, now)` returns the most recent anchored slot ≤ `now`:
  - weekly with weekday + hour → last `{weekday} {hour}:00 UTC`;
  - daily with hour → last `{hour}:00 UTC`;
  - otherwise `null`, meaning the legacy interval rule applies (monthly, or no anchor set).
- `isProjectDue` with a slot: due iff `lastSuccessfulRunAt` is null, **or**
  `lastSuccessfulRunAt < slot − DUE_TOLERANCE_MS`, where the slot is computed at
  `now + DUE_TOLERANCE_MS`. Without an anchor, the existing interval rule is unchanged.
- `isProjectStale` with a slot: stale iff `now > slot + STALE_GRACE_MS` and
  `lastSuccessfulRunAt < slot − DUE_TOLERANCE_MS`.

Worked example (`weekly`, `monday`, `4`, tolerance 30 min):

| Tick (UTC)                         | Slot used          | Last success          | Due?               |
| ---------------------------------- | ------------------ | --------------------- | ------------------ |
| Mon 03:00:10                       | previous Mon 04:00 | previous Mon 04:00:40 | no                 |
| Mon 03:59:50 (early)               | Mon 04:00          | previous Mon 04:00:40 | yes                |
| Mon 04:00:20                       | Mon 04:00          | previous Mon 04:00:40 | yes                |
| Mon 05:00:10                       | Mon 04:00          | Mon 04:00:20          | no                 |
| Mon 05:00 after a failed 04:00 run | Mon 04:00          | previous Mon          | yes (hourly retry) |

The watermark is the run **start** time (existing behaviour), so a successful Monday run is
never due again that week. The cadence cannot drift, because the slot comes from the
calendar, not from `last + 7 days`.

**Migration of the live project**: no code or data migration. After deploy, the owner sets
`hht` to `schedule: weekly`, `publishWeekday: monday`, `publishHourUtc: 4` in the admin. The
existing digests (2026-08-31, 2026-09-22) stay as historical issues and get issue text from the
backfill sweep (R2). The next run's window starts at each source's `lastSuccessfulFetchAt`, so
the first Monday issue contains every relevant item not already in an earlier digest. Nothing
is skipped and nothing is duplicated (dedupe).

**Rationale**: The planning notes ask for no hardcoded HHT schedule and no extra Scheduler jobs
(free tier ≤ 3). Nullable fields keep every other project on today's behaviour.

**Alternatives considered**:

- _One Cloud Scheduler job per project (cron `0 4 * * 1`)._ Rejected: free-tier job count,
  per-project infra drift, and it moves product config out of the CMS.
- _Hardcode Monday 04:00 in `schedule.ts`._ Rejected: planning notes and Principle V.
- _Keep `last + 7d` and snap the watermark to the slot._ Rejected: the watermark is also the fetch
  window start. Snapping it backwards would re-fetch an hour and blur two meanings of one
  field.

## R6 — Issue-text translation runs on request in the web app

**Decision**: The web app translates issue text (summary points and item sentences) into
`de/tr/ru/uk` on the first request for that issue and locale, and caches the result in a new
`issue-translations` collection. It uses the `ai` and `@ai-sdk/gateway` packages already in
`apps/web/package.json`, with `AI_GATEWAY_API_KEY` and `AI_GATEWAY_MODEL` set on Vercel (as
`docs/deploy-worker.md` anticipated). Publication-level translations (titles and specialist
summaries in `content-translations`) are **unchanged**. The worker still pre-generates them;
see R17.

**Rationale**: FR-012 requires translation on first request with an in-render wait. Only the
web app sees the request. It matches Constitution III/VI ("translate on first request") and
closes roadmap F18 for the new text.

**Alternatives considered**:

- _Worker pre-translates all four locales at generation time._ Rejected: contradicts FR-012 and
  Constitution III/VI, and wastes spend for locales nobody opens.
- _Machine-translation link only (`translationFallback.ts`)._ Rejected: that is a fallback, not
  a translation.

## R7 — Single-flight is enforced by a unique index in Postgres

**Decision**: `issue-translations` has a compound unique index on `(digest, locale)`
(`indexes: [{ fields: ['digest', 'locale'], unique: true }]`, supported in Payload 3.88). One row
represents one issue+locale translation, in state `pending`, `ready` or `failed`. The **insert
is the lock**:

1. **Read** the row for `(digest, locale)`.
   - `ready` and `sourceRevision === digest.issueTextRevision` → serve it.
   - `pending` with `leaseExpiresAt > now` → someone else is translating; go to wait (R8).
   - `failed` with `retryAfter > now` → serve English with the note, and do not retry.
   - Anything else (lease expired, cooldown over, revision mismatch) → **reclaim**: delete that
     row **by its id**, then continue to step 2.
   - No row → step 2.
2. **Claim**: `create` a row `{ status: 'pending', sourceRevision, leaseExpiresAt: now + 120 s }`.
   - Success → this request owns the translation (R8).
   - Error → re-read. If a row now exists, another instance won; go to wait. Otherwise rethrow.
3. **Owner finishes**: `update` by the claimed row's id to `ready` with the translated text, or
   to `failed` with `retryAfter: now + 15 min` and `error`. If the update finds no row (it was
   invalidated by an edit, R9), the result is discarded.

**Why this holds across Vercel instances**: two concurrent instances can both decide to reclaim
or claim, but Postgres lets exactly one `INSERT` of a given `(digest, locale)` succeed. The
reclaim deletes by the **old row's id**, so a slow reclaimer can never delete a fresh claim
made by someone else. At most one LLM translation runs per pair at a time. After it completes,
no new one starts until the text revision changes or a failure cooldown expires (FR-012 "at most
once").

The error for a unique violation from the Postgres adapter is not a stable public type. So the
code does not parse it: "create failed, and a row exists on re-read" is the lost-race signal.

**Alternatives considered**:

- _In-memory promise map / `React.cache`._ Rejected: per instance only (planning notes).
- _Postgres advisory locks via raw SQL._ Rejected: needs a held connection across an LLM call on
  a pooled serverless connection, and couples to the Drizzle internals.
- _Conditional `UPDATE … WHERE status …` via `payload.db.drizzle`._ Rejected: raw SQL against
  Payload-generated table names. The unique insert gives the same guarantee through the public
  Local API.
- _Upstash/Redis lock._ Rejected: a new vendor for one lock (Principles III, VIII).

## R8 — Wait up to 8 s, then fall back; `after()` keeps the work alive

**Decision**: In `GET /api/public/projects/:slug/issues/:id?locale=xx` (route handler,
`export const maxDuration = 60`):

- `deadline = requestStart + ISSUE_TRANSLATION_WAIT_MS` (8,000 ms).
- **Owner path**: start `translateAndStore()` as a promise and register it with
  `after(promise)` from `next/server`. Then `await Promise.race([promise, sleepUntil(deadline)])`.
  If it resolved, respond translated. Otherwise respond English with
  `translation: { status: 'pending' }`. The promise keeps running after the response, because
  `after()` maps to Vercel's `waitUntil`.
- **Waiter path** (lost the race or found a live lease): poll the row every 400 ms until `ready`,
  `failed`, or the deadline passes.
- **Crawlers** get exactly the same code path. There is no user-agent branching (FR-012).
- **List endpoints never trigger a translation.** The archive and the project page's latest-issue
  card use a cached translation if one exists, and English with the note otherwise. This keeps
  a listing from fanning out into N LLM calls.

The page and `generateMetadata` share one fetch per request through React `cache()`, so a
crawler hit causes one API call and one wait, not two.

**Rationale**: Matches the clarification exactly (≈ 8 s wait, background completion,
same for crawlers). `after()` is the Next-native, portable form of `waitUntil`. It also works
under `next start` in Docker (Principle VIII).

**Alternatives considered**:

- _Always respond immediately in English and translate in the background._ Rejected: the
  clarified behaviour is wait-then-fallback.
- _Translate in the page component instead of the route handler._ Rejected: pages already read
  through `/api/public/...` (002 R1, 003 R2). Keeping one contract lets Playwright hit the
  same surface.

## R9 — Edits and regeneration invalidate translations in the same transaction

**Decision**:

- `issueTextRevision` (number, system-managed) is bumped in the `Digests` `beforeChange` hook
  whenever the English `issueSummaryPoints` or `issueItemSentences` differ from `originalDoc`.
  This applies to both owner edits and worker regenerations. The worker always sends
  `issueTextSource: 'generated'`.
- An **owner** text edit (an admin session; worker writes are the header-only key or a user
  with the `worker` role)
  also sets `issueTextSource: 'edited'` and `issueTextStatus: 'ready'` and resets attempts.
  The admin form submits every field, so a missing `issueTextSource` cannot be the signal.
  Forcing `ready` matters for `pending`/`failed` digests: otherwise a hand-written summary is not
  rendered (only `ready` renders) and the next sweep overwrites it. An explicit re-queue to
  `pending` in the same save wins.
- When the owner changes `issueTextStatus` to `pending` (regenerate), the hook resets
  `issueTextAttempts` to 0.
- `afterChange` (update, revision changed) deletes all `issue-translations` rows for that digest
  via `req.payload.db.deleteMany({ …, req })`. It shares `req`, which is the documented 504 lesson
  in `digestHooks.ts`.
- Readers also check `row.sourceRevision === digest.issueTextRevision`, so a translation that
  was in flight during an edit is never served even in the gap before deletion.

**Rationale**: FR-021 says "invalidate immediately". Deleting rows inside the same transaction
as the edit makes the next request see "no row" and start a fresh claim (R7). Keeping a revision
number on both sides is cheap insurance against races.

**Alternatives considered**: _Keep old rows and filter by revision._ Rejected: the unique
`(digest, locale)` index then needs `sourceRevision` in the key. That allows one row per
revision, and stale rows pile up.

## R10 — Hiding an issue hides only the issue

**Decision**: New `hiddenFromPublic` checkbox on `digests` (default `false`). When it is `true`,
the issue detail endpoint returns 404 (the same body as unknown, as in 003 R3), the archive and
latest-issue queries exclude it, and its page 404s. Its OG image URL serves the generic project
card (contract issue-pages §5), which reveals nothing about the hidden issue. `feedPublishedAt` on its
publications is **not** touched, so its materials stay in the flat feed and their detail pages
keep working (planning notes). The worker still generates text for hidden digests, so unhiding
shows a complete page.

**Rationale**: Materials are factual source entries. Hiding is about the generated issue text.
Leaving `feedPublishedAt` alone also keeps `hasPublishedDigest` and `/api/health` semantics
unchanged.

## R11 — Localized metadata, with Telegram added to the blocking-metadata bot list

**Decision**:

- `[locale]/layout.tsx` exports `generateMetadata`: `metadataBase` from `getPublicSiteUrl()`, a
  localized `title.template` and `default`, a localized description, `alternates.languages` for
  the five locales, and `openGraph.locale`.
- Every covered page exports `generateMetadata`: home, project, archive, issue, and material
  detail. Each sets `title`, `description`, `openGraph` (type, title, description, url,
  siteName, locale) and `twitter` (`summary_large_image`). The image comes from the file-based
  `opengraph-image` (R12).
- **Bots**: Next 16 streams metadata into `<body>` for user agents not in
  `htmlLimitedBots`. The built-in list (checked in
  `next/dist/shared/lib/router/utils/html-bots.js`) includes `WhatsApp`, `facebookexternalhit`,
  `vkShare`, `Twitterbot`, but **not `TelegramBot`**. `next.config.ts` sets `htmlLimitedBots`
  to the built-in pattern plus `TelegramBot` and `Viber`, so every target chat app receives
  `<head>` metadata before any HTML streams.

**Rationale**: FR-009 and SC-001. Without the Telegram entry, the most important chat app for
the audience could see metadata outside `<head>`.

**Consequence to manage**: for these bots the render is blocking, so a crawler receives no
bytes until metadata resolves. On the first request for an untranslated locale that includes
the up-to-8 s translation wait (R8) plus the page's call to its own API. Some preview crawlers
may time out sooner and show no preview. This is the behaviour chosen in the clarify session,
so the logic stays. The operational mitigation is in the rollout checklist (quickstart §7): open
the issue in the chat's locale before posting the link, so the translation is cached and the
crawler gets a fast response. The first real Telegram check is made on a locale with no cached
translation, to learn whether this matters in practice.

## R12 — OG images come from `next/og`; no uploads or blob storage

**Decision**: File-based metadata images rendered with `ImageResponse` (`next/og`, Node
runtime):

- `app/[locale]/opengraph-image.tsx`: site card.
- `app/[locale]/projects/[slug]/opengraph-image.tsx`: **default project image** (project name +
  localized tagline). The material detail pages and the archive are meant to inherit it.
  **Risk to verify**: those pages set their own `openGraph` in `generateMetadata`, and a child's
  `openGraph` object replaces the parent's, which can drop the inherited `og:image`. The shared
  metadata builder (`lib/metadata.ts`) must therefore either leave `openGraph.images` to the file
  convention and be proven by test to keep it, or set `images` explicitly to the project image
  URL (`/{locale}/projects/{slug}/opengraph-image`). `share-metadata.spec.ts` asserts an
  absolute `og:image` on the **material detail and archive pages** as well as the issue page
  (R16).
- `app/[locale]/projects/[slug]/issues/[issueId]/opengraph-image.tsx`: **per-issue image**
  (project name, localized issue date, localized "N new materials"). If loading the issue fails
  or it is hidden, it renders the project card instead (FR-010 fallback).

The images use no generated summary text, so they never wait for a translation. Fonts:
IBM Plex Sans Regular and SemiBold TTF (OFL; they cover Latin Extended for Turkish and Cyrillic
for ru/uk) in `apps/web/assets/fonts/`. They are read with `fs.readFile` and included in the
function bundle via `outputFileTracingIncludes`. Output is 1200×630 PNG, which is well under
WhatsApp's ~300 KB preview limit.

**Rationale**: "Generated per issue" at zero storage cost, with no Media collection and no
Vercel Blob (Principle III). Next file conventions handle the absolute `og:image` URL and the
dimensions. `opengraph-image` does **not** emit `twitter:image` (that is the separate
`twitter-image` convention). This is acceptable: none of the target chat apps reads
`twitter:*`, and X falls back to `og:image`. No `twitter-image` files are added.

**Alternatives considered**:

- _Payload upload collection + Vercel Blob for a default image._ Rejected: a storage adapter and
  a new vendor surface for a static card.
- _AI-generated illustration per issue._ Rejected: spend, and medically themed imagery is a
  trust risk. The spec allows a default.

## R13 — Trust notice and plain chrome are static, localized messages

**Decision**: A `TrustNotice` server component renders the disclaimer and the AI-generated
label from new `Trust.*` messages in all five locales. It appears on the issue page (below the
summary and at the end) and on the material detail page. The hardcoded header "Research
Monitoring" in `[locale]/layout.tsx` becomes `Site.name`. `Home` and `Project` strings are
rewritten for patients with no disease names. The project name comes from data, as in
"Weekly research updates: {projectName}".

**Rationale**: FR-011, FR-017, FR-018, roadmap §1.2 #8–9. Static strings go through next-intl
like all other chrome. None of this needs the AI translation path.

## R14 — One shared comparator for issue order

**Decision**: `packages/shared` exports `compareIssueItems`: raw importance rank first
(`critical` > `high` > `medium` > `low` > missing), then `publishedOrUpdatedAt` newest first
(nulls last), then id as a stable tie-break. The worker uses it to number items for the prompt.
The web app uses it to order the issue list. `sourceType === 'clinicaltrials'` sets
`isTrialRegistration: true`, which drives a visible "Registered study" label next to the
source badge.

**Rationale**: FR-008 says "existing importance value". The four-level raw value is the
existing value; the two-level display collapse is a feed presentation choice. A shared
comparator guarantees that "item 3" in the prompt is item 3 on the page.

## R15 — Additive schema only; either deploy order is safe

**Decision**:

- Only **add** fields, one collection, and one index: new nullable columns and array
  sub-tables on `digests`, new nullable columns on `research-projects`, and a new
  `issue_translations` table with its sub-tables and unique index. No renames, no removals, and
  no new options on existing select enums. Drizzle push then has no rename prompts and no
  data-dependent steps. Production gets it from `ensure-schema` in the Vercel build. Preview
  builds push into their `preview/<branch>` Neon branch.
- The `Digests` `beforeValidate` "empty digest" check currently throws on **any** PATCH that
  omits `publications`. It becomes create-only (or only when `publications` is present). Without
  this, the worker's issue-text PATCH would be rejected.
- **Deploy-order safety.** Vercel (schema push) and the worker image (`deploy-worker.yml`) both
  deploy on merge, in either order:
  - _New worker, old web_: the anchor fields read as `undefined` (legacy interval). The old
    Payload rejects the sweep's `where[issueTextStatus]` query with **400** (unknown query
    path). The sweep treats a 400 from its selection query as "web not upgraded yet": it logs
    **WARN** `sweep skipped: cms rejected query` and returns. It must not log ERROR, because
    ERROR fires the log-based alert and this state is expected for a few minutes during a
    deploy. 5xx and network errors stay ERROR (`sweep list failed`). No digest is PATCHed in
    this state, so the old `beforeValidate` never sees an issue-text PATCH.
  - _Old worker, new web_: new digests are created with the default status `pending`. The next
    new-worker sweep fills them.
- Existing digest rows get the column default or `NULL` for `issueTextStatus`, depending on how
  push emits defaults. The sweep query treats both `pending` and "does not exist" as pending.

**Rationale**: Planning notes (additive, Neon preview branch, ensure-schema on deploy).

## R16 — Test strategy: pure logic in Jest, the DB guarantee in seeded Playwright

**Decision**:

- **Jest (`packages/shared`)**: `latestScheduledSlot`, `isProjectDue` / `isProjectStale` with and
  without anchors (the R5 table, DST-free by construction because it is UTC), and
  `compareIssueItems`.
- **Jest (`apps/worker`)**: issue-text validation and mapping (R3), the guard patterns, sweep
  selection, and status transitions with a fake CMS client.
- **Jest (`apps/web`)**: the claim/wait state machine (R7/R8) against an in-memory store that
  enforces the same unique key. Also locale resolution for issue text, the revision-bump
  decision in the `Digests` hook, and issue DTO mapping.
- **Playwright (`apps/web`)**, seeded: the issue page (summary → anchors → items → detail),
  hidden → 404 while its materials stay in the feed, the archive order, the trust notice on
  issue and detail pages in 5 locales, OG tags with a `TelegramBot` user agent on the issue,
  archive **and material detail** pages (R12 inheritance risk), a 360 px viewport with
  JavaScript disabled, and **single-flight**: 8 concurrent `GET`s for one untranslated
  issue+locale → exactly one `issue-translations` row with `attempts === 1`.
- **Single-flight test isolation.** CI runs Playwright with `retries: 2` against shared seed
  data, so a retry would find the row left by the first attempt and fail `attempts === 1`.
  Each run of the spec must start from "no row": the seed creates a dedicated digest used only
  by this spec, and the spec clears its rows first through a test-only reset. The reset is a
  route under `/api/test/…` that exists only when `ISSUE_TRANSLATOR=stub` and never when
  `VERCEL_ENV === 'production'` (same guard as the stub). `issue-translations` denies REST
  writes and deleting needs a session, so there is no other anonymous path. The spec reads the
  row count and `attempts` through the same test route.
- **What CI proves.** CI runs one `next start` process, so it proves the database constraint
  under concurrent requests (the code has no in-process dedupe that could mask it). The
  **cross-instance** check (two servers on different ports) stays a manual step in quickstart
  §3.
- **Translator stub** for tests: `ISSUE_TRANSLATOR=stub` (with `ISSUE_TRANSLATOR_STUB_DELAY_MS`)
  returns deterministic `[ru] …` text. It refuses to activate when `VERCEL_ENV === 'production'`.
- **CI**: add `pnpm --filter @hht/web seed:public-feed` after `ensure-schema` so the seeded specs,
  including the single-flight spec, run in the required check instead of skipping. The seed
  already refuses non-local databases. This strengthens Layer 3 and weakens nothing. Side
  effect: the existing seeded tests in `public-feed`, `public-material-detail` and
  `monitoring-digest` stop skipping in CI. Turning the seed on is therefore its **own first
  task**, before any feature code. Anything that then fails is fixed there, not mixed into the
  feature work.

**Rationale**: The single-flight property can only be proven against real Postgres. CI already
runs one, and seeding it is the smallest change that turns the proof into a required check.
